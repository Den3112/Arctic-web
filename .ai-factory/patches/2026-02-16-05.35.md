# Project Deletion Fails with Foreign Key Constraint & Unresponsive UI

**Date:** 2026-02-16 05:35
**Files:** src/actions/projects.ts, src/components/features/projects/ProjectList.tsx, src/components/ui/alert-dialog.tsx
**Severity:** high

## Problem

1.  **Backend:** Deleting a project with existing time entries failed silently (or with a 500 error in logs) due to a database Foreign Key constraint violation.
2.  **Frontend:** The user clicked the delete button, but "nothing happened". The native `window.confirm` dialog was used (which can be flaky or blocked), and there was no visual feedback (loading state) to indicate the request was processing or failing.

## Root Cause

1.  **Database Constraint:** The `time_entries` table references `projects(id)` but relies on the default strict behavior (RESTRICT) instead of `ON DELETE CASCADE`. A planned "Soft Delete" migration (adding `deleted_at`) was missing from the environment, so the code's soft delete logic failed, and hard delete was blocked.
2.  **UI/UX Gap:** The `handleDelete` function triggered an async server action but did not manage a `loading` state. If the server action failed (due to the FK issue), the error was caught but might not have been toasted effectively, or the native confirm dialog provided a poor experience.

## Solution

## Solution

1.  **Soft Delete Strategy**: Switched from Hard Delete to Soft Delete. Updated `deleteProjectAction` to set `deleted_at` timestamp on both `projects` and associated `time_entries`. This bypasses Foreign Key constraints safely and prevents data loss.
2.  **Filtering**: Updated `getProjects` to explicitly filter out soft-deleted projects (`.is('deleted_at', null)`), resolving the issue where deleted projects persisted in the UI.
3.  **Modern UI Component**: Replaced `window.confirm` with a custom `AlertDialog` component (`src/components/ui/alert-dialog.tsx`) to provide better feedback.
4.  **Visual Feedback**: Added `isDeleting` loading state to the delete button.
5.  **Logging**: Added `[FIX]` prefixed logging for observability.

## Prevention

- **Database Design**: Ensure Foreign Key constraints match the deletion strategy (Cascade vs. Soft Delete). If Soft Delete is intended, ensure migrations are applying `deleted_at` columns consistently.
- **UI Patterns**: Always use visual feedback (loading spinners, disabled states) for destructive async operations. Avoid native `alert`/`confirm` in modern web apps as they block the main thread and are hard to style/test.
- **Testing**: E2E tests should cover "delete with dependencies" scenarios to catch constraint violations early.
